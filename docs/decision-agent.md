# Decision agent

CIMT owns scenario execution, device interaction, observation, the command queue, evidence and stopping. A replaceable decision agent receives a `DecisionRequest` and returns the next normalized CIMT command dictionary; an ordered batch uses the existing `queuedCommands` convention. It does not need CIMT-specific mutable attributes or completion-review or proposal methods. The structural `DecisionAgent` protocol in `runtime/decision_agent.py` defines `check_access()` and `decide(request)`. `check_access` must not execute a test or a paid inference.

`DecisionRequest` contains the testing instructions, requirements, setup, fresh masked screenshot and UI elements, history, aliases (not credential values), coverage, feedback and exploration context. Mutable observation and context data are deep-copied before delivery so agent-side edits cannot change live scenario evidence. It also supplies the shared deadline, cancellation check and budget. The optional request observer and timing callback support recording provider requests. `request.arguments()` is a compatibility helper for the existing OpenAI prompt builder, not a requirement on alternative agents.

`Execution(..., agent_factory=..., budget_factory=...)` supplies a decision agent factory and, when needed, a compatible shared budget factory. The factory is called for preflight and once per device worker; it must return independent per-worker agents implementing the protocol. The default `Agent` uses OpenAI; completion review uses a separate reviewer from `review_factory`, and the post-run proposal uses its own generator through separate proposal and budget factories. All default services share the existing run budget and accounting. The decision agent and in-run reviewer check shared stop before provider transport. An output-limit retry uses the same check. A reservation is released if a stop prevents the request from being sent. Device dispatch and review do not call methods on the decision agent beyond the protocol.

A third-party engine still needs an adapter that maps these inputs and outputs to its own API. It must honor the deadline, shared stop and budget before billable requests, account for actual and uncertain usage, use masked evidence and aliases, and preserve appropriately redacted request and response records. The existing `RequestJournal` recognizes the current OpenAI request format; a different provider requires a qualified recorder and pricing/accounting implementation. Arbitrary external processes are not sandboxed or automatically prevented from spending. CIMT's built-in budget currently supports its configured priced models, not every provider. Completion review and proposals remain configured separately; replacing the decision agent alone does not replace those services.

Supplying a custom agent is currently a Python composition/integration change, not a YAML plugin selector. A full engine that owns its own device loop, such as Arbigent, cannot simply be passed as this decision agent; it needs an integration that preserves CIMT's execution ownership and policy, or a separate execution-engine boundary. No live comparison or third-party compatibility is claimed by the offline contract tests.

## Registered tools

The default OpenAI agent registers the device commands as SDK function tools. Android also offers `back` and `sample_memory`. The SDK returns each tool call as a normalized CIMT command and ends that model turn. CIMT dispatches it through the existing command queue and sends the observed result as a matching function output with the next decision and fresh evidence. This preserves cancellation, device checks and reporting, and adds no acknowledgement inference. Tool definitions and result items are included in the normal input token count.

JSON command batches, planning and completion commands remain available. The registrar and Responses API serialization live in `runtime/agent_tools.py`. A different decision agent can ignore the optional previous tool result field on `DecisionRequest`.
